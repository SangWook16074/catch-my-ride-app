# ADR-001 — 스토어판 플랫폼 아키텍처: Flutter 전면 + 시스템 서비스만 네이티브

- **상태**: 승인 (2026-09-08, 오너 결정)
- **적용 대상**: 놓치지마 스토어 출시용 앱 (`catch_my_ride/` — 앱인토스 미니앱과 별개 코드베이스)
- **관련 문서**: [PRD.md](../../PRD.md) · [API.md](../../API.md) · 하네스 문서 [CLAUDE.md](../CLAUDE.md)

## 맥락

앱인토스 미니앱(catch-my-ride-appintoss)으로 검증한 놓치지마를 **iOS·Android 스토어 앱**으로
개발한다. 조건:

1. 두 플랫폼 동시 출시, 개발 인력은 사실상 1인.
2. 각 플랫폼 유저에게 그 플랫폼다운 UX를 주고 싶다 — 특히 **iOS는 리퀴드 글라스 위젯 경험**
   (iOS 26 시스템 머티리얼)이 목표.
3. 서버는 기존 catch-my-ride-server(REST, [API.md](../../API.md))를 그대로 쓴다.
4. 오너의 주 스택은 Flutter.

## 검토한 선택지

| # | 안 | 평가 |
|---|---|---|
| A | 비즈니스 로직 Flutter + UI 전반 Native | ❌ 모든 화면이 MethodChannel 브리지를 넘는다. 화면 하나에 Dart+Swift+Kotlin 3중 유지보수 — Flutter를 쓰는 이유(한 번 작성)를 상쇄. 1인 개발에 최악 |
| B | 공통 UI Flutter + 특화 화면만 Platform View | ⚠️ A보다 낫지만 "화면 단위" 분할은 위험. Platform View는 임베드용 도구라 스크롤·제스처·키보드·z-order 상호작용 문제를 화면 수만큼 떠안는다 |
| C | Kotlin Multiplatform (공유 로직 + SwiftUI/Compose UI) | ⚠️ "공유 로직 + 네이티브 UI"의 정석 도구지만 오너 스택(Flutter)과 불일치. UI 2벌 작성은 여전히 1인 규모 초과 |
| D | **Flutter UI 전면 + 플랫폼 적응형 + 시스템 서비스만 네이티브** | ✅ 채택 |

## 결정

**D안.** 구체적으로:

1. **앱 내부 화면은 전부 Flutter**로 작성한다. 플랫폼다움은 적응형 설계로 준다 —
   iOS에서 Cupertino 스타일 내비게이션·스위치·피커(`.adaptive` 생성자), 스와이프 백,
   플랫폼별 페이지 전환, 햅틱.
2. **네이티브 코드는 "화면"이 아니라 "시스템 서비스"에만** 쓴다:
   - **iOS Widget Extension** (SwiftUI + WidgetKit) — 홈/잠금화면 위젯.
     iOS 26 리퀴드 글라스는 시스템이 위젯에 자동 적용 → 목표 UX가 여기서 달성된다
   - **iOS Live Activity** (SwiftUI + ActivityKit) — 출발 임박 카운트다운을
     잠금화면·Dynamic Island에 실시간 표시. 놓치지마의 킬러 기능 후보
   - **Android 홈 위젯** (Glance/Compose)
   - 푸시 알림 채널·백그라운드 갱신 등 OS 통합
3. **Platform View는 허용 목록 방식**: 네이티브 SDK가 뷰를 직접 그리는 임베드
   (지도, 웹뷰, 광고)에만 허용. "iOS답게 만들고 싶어서" 일반 화면을 Platform View로
   만드는 것은 금지 — 필요하면 이 ADR을 개정한다.
4. 앱 ↔ 위젯 데이터는 **App Group(iOS)/공유 저장소(Android)** 로 공유하고,
   Flutter 쪽은 `home_widget` 계열 패키지로 갱신만 트리거한다.

## 결정의 핵심 근거

- **위젯·Live Activity는 프레임워크와 무관하게 네이티브 전용이다.** WidgetKit 위젯은
  앱 프로세스 밖 Extension에서 시스템이 렌더링하므로 순수 네이티브 앱이었어도 SwiftUI로
  따로 만든다. 즉 **위젯 품질에서 Flutter 앱과 네이티브 앱의 차이는 0** — 리퀴드 글라스
  위젯이라는 목표가 하이브리드 인앱 UI를 요구하지 않는다.
- 놓치지마의 화면(온보딩 위저드·라이브 뷰·설정)은 적응형 Flutter로 충분한 복잡도다.
- 유저가 리퀴드 글라스를 체감하는 표면은 시스템 크롬(위젯·알림·시트·홈화면)이 압도적이다.

## 감수하는 트레이드오프

- **앱 내부의 진짜 리퀴드 글라스(동적 굴절·주변 콘텐츠 반응)는 포기.** 시스템 머티리얼이라
  Flutter로는 블러+반투명 근사치까지만 간다. 인앱 근사치 + 시스템 표면의 진짜 글라스 조합으로
  충분하다고 판단.
- 위젯·Live Activity를 만들 때 SwiftUI·Glance 학습 비용 발생 — 단, 화면 전체가 아니라
  카드 몇 장 수준의 코드 양이다.

## 재검토 트리거

다음 상황이면 이 ADR을 개정한다:

1. 특정 인앱 화면의 적응형 근사치가 유저 피드백에서 반복적으로 어색하다고 확인될 때
   → 그 화면 하나만 Platform View 허용 목록에 추가 (전면 전환 아님)
2. 팀이 2인 이상으로 늘고 네이티브 전담이 가능해질 때 → C안(KMP) 재평가
3. Flutter의 위젯 브리지 생태계(home_widget 등)가 Live Activity 요구를 못 받칠 때
   → Extension 쪽 코드 비중 확대
